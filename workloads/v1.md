# Workload v1: Setpoint RPC and Sample telemetry

All integer fields are unsigned 32-bit values. Each implementation uses its
native schema and wire format. Application behavior, limits, and checks are
shared.

## Setpoint RPC

Request: `request_id`, `channel`, `value`. Response: `request_id`, `status`,
`applied_value`. Valid calls use a nonzero request ID, channels 0..3, and
values 0..100000. A valid request succeeds with status 0, echoed request ID,
and applied value equal to the requested value. A request outside the range
returns status 1 and applied value 0. A response with the wrong ID/value or a
missing/duplicate response is a correctness failure, not a timing sample.

The benchmark server owns a four-entry array of channel setpoints. The
operation updates one entry on success. Warmup and timed iterations use the
same behavior, but timed requests vary request ID and channel. Four concurrent
client calls is the target capacity for the later concurrency scenario; the
first latency scenario has one outstanding call. The server does no logging.
Any allocation required by a library's generated ownership contract stays in
the measured path and is reported (eRPC allocates response storage this way).

## Sample telemetry

Message: `sequence`, `sample_tick`, `value`, `flags`. Sequences are monotonic
within a run. `sample_tick` is a logical 32-bit sampling tick, not a wall clock.
`value` is 0..100000; `flags` uses only the low eight bits. The receiver checks
all four fields against a deterministic generator and counts accepted,
duplicate, missing, and malformed samples. There is no application response.

## Transport and measurements (next milestone)

The first hardware pass uses two ESP32-S3 DevKitC boards with the same UART
baud rate and a fixed maximum application body of 64 bytes. Record the actual
framing, CRC, reliability, timeout, buffer sizes, and thread model per library.
Start with a clean link; introduce controlled loss only after equivalent
reliability behavior is implemented. A one-way send and a completed RPC must
never be compared as the same operation.

Collect RPC completion p50/p95/p99, calls/s, CPU cycles per endpoint, encoded
bytes per direction, Flash, static RAM, maximum stack, and runtime allocations.
For telemetry collect accepted messages/s, end-to-end age when synchronized
measurement is available, encoded bytes, CPU, and drop/duplicate counts. Store
raw observations and the exact build/run manifest before deriving summaries.

Timing starts immediately before admission to the library-facing client API
and stops after the validated response is available to application code. The
telemetry sender timing starts before encoding/admission and stops when the
library reports the outbound unit accepted; receiver processing is measured
separately. Record setup cost separately. Each row must name whether framing,
CRC, retries, and business codec are inside the measured boundary.
